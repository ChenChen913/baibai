# 地图「探照灯」朝向指示方案（罗盘光锥）

> 需求：仿高德/百度地图——手机朝向哪儿，地图上当前位置就向哪个方向打出一束「探照灯光锥」，随手机旋转实时调整。
> 本文档只做方案设计，**未动任何代码**，等用户批准后实施。

---

## 一、需求本质与现状

### 1.1 这个效果的技术本质

高德/百度的「探照灯」= **设备罗盘朝向可视化**：

- 数据源：手机内置**磁力计 + 加速度计**（融合成朝向角 azimuth，即设备顶端指向相对真北的角度）
- 注意：**不是 GPS 航向（bearing）**。bearing 是「移动方向」，静止时无效——转手机它不会动，做不出「手机朝哪儿灯朝哪儿」的效果。所以**必须用磁力传感器**。

### 1.2 项目现状盘点（已核实）

| 端 | 位置点实现 | 朝向数据 | 结论 |
|---|---|---|---|
| 网页版 `src/map-ui.ts` | `L.divIcon`（红点 + 呼吸脉冲 + 精度圈） | 无 | 渲染层改动小：DivIcon 内加一层光锥 div，JS 只改 `transform: rotate()` |
| 安卓版 `map.html`（WebView） | `L.circleMarker`（红圆 + 精度圈） | 无；`LocationSource.kt` 只有定位，无任何传感器代码 | 需两步：①原生接传感器 ②经 JS bridge（`BaibaiMap.xxx` 现成先例）推给地图 |

两端地图坐标系（WGS-84/GCJ-02 双图层）与光锥**无关**——光锥只管旋转角度，不碰坐标转换，这是本功能的一个利好。

## 二、三个方案

### 方案一（推荐）：双端原生传感器 + CSS 光锥渲染

**思路**：Android 用系统传感器 API 拿朝向，Web 用浏览器 DeviceOrientation API 拿朝向，渲染统一用「DivIcon + CSS transform 旋转光锥」。

**实现路径**：

**① 安卓端（主战场，先行）**

1. 新建 `HeadingSource.kt`（或并入 `LocationService`）：
   - `SensorManager` 注册 `TYPE_ROTATION_VECTOR`（系统已融合磁力计+加速度计，无需自己写互补滤波）
   - `getRotationMatrixFromVector` → `getOrientation` → azimuth[0]（弧度）
   - 加 `GeomagneticField` 磁偏角校正（真北 vs 磁北，国内约 -7°~+11°，不校正指向会偏）
   - 节流：传感器 ~50Hz 降频到 **10~15Hz** 推送（省电 + WebView evaluateJavascript 开销可控）
2. bridge：`RecorderHub` 暴露朝向 StateFlow → `RecordScreen` 里现有的 1.2s 轮询不适用（太慢），改为传感器回调直接 `w.evaluateJavascript("BaibaiMap.setHeading(deg)")`
3. `map.html`：`drawMe` 里把 `circleMarker` 升级为 `divIcon`（红点 + 光锥层），新增 `setHeading(deg)` 只改光锥的 `style.transform`——**不重建 DOM、不重绘地图，性能无损**
4. 生命周期：进入记录页注册传感器，离开/暂停时注销（省电）；`AndroidManifest` 无需新权限（传感器不需要权限声明）

**② 网页版（第二步）**

1. `src/gps.ts` 或新建 `src/heading.ts`：
   - iOS 13+：`DeviceOrientationEvent.requestPermission()` 拿 `webkitCompassHeading`（真北、顺时针）——**必须在用户手势内调用**，挂到「开始拜年」按钮点击时请求（正好是用户注意力焦点，自然）
   - Android Chrome：`deviceorientationabsolute` 事件的 `alpha`（真北 = 360 - alpha，注意它是逆时针）
   - 桌面/不支持：静默降级不显示光锥
2. `map-ui.ts`：DivIcon 里加光锥层，`setHeading(deg)` 同安卓实现

**③ 两端共用的渲染与平滑（JS 同一套思路）**

- **角度平滑**：指数低通滤波（α≈0.25）消磁力计抖动
- **最短弧插值**：359°→1° 必须顺转 2°，不能逆转 358°（wrap-around 经典坑）
- **屏幕方向补偿**：安卓已锁竖屏（H-5）可跳过；Web 未锁，用 `screen.orientation.angle` 补偿
- **校准检测**：磁力计未校准（如 `webkitCompassHeading.accuracy` 差 / 罗盘干扰）时光锥降透明度提示「∞ 干扰」或隐藏

**需要的条件**：
- 安卓：真机（模拟器没有磁力计；`TYPE_ROTATION_VECTOR` 模拟器返回空）
- Web：HTTPS（已有 GitHub Pages）+ iOS 需用户点一次「允许」
- 开发机：无需新依赖、无需新权限申请

**难度评估**：
- 安卓部分：**3/10**——系统 API 成熟，bridge 有现成先例，无权限坑
- Web 部分：**5/10**——iOS 权限流程 + 浏览器碎片化（各家 WebView 对 absolute orientation 支持参差）是主要工作量的坑
- 渲染/平滑：**2/10**——纯 CSS + 初等数学

### 方案二：仅 GPS 航向（bearing）箭头

**思路**：用连续定位点连线的移动方向画箭头，不接传感器。

**实现路径**：定位回调里已有点序列，取最近两点算 atan2，旋转箭头。工作量最小。

**致命缺陷**：**静止时转手机，箭头不动**（bearing 只在移动时有效）——用户明确要「手机朝向哪儿灯朝哪儿」，此方案不满足核心需求。仅适合作为方案一里传感器不可用时的移动中兜底（高德实际是罗盘+bearing 双模融合）。

**难度**：2/10，但**功能不达标，不推荐单独采用**。

### 方案三：罗盘 + GPS 航向融合校准（高德完全体）

**思路**：方案一基础上，移动速度 > 1.5m/s 时用 GPS bearing 反推磁偏角自动校准罗盘漂移。

**难度**：7/10。校准环（Kalman 或简单加权）调参成本高，对步行拜年场景收益边际——**过度工程，不推荐**。磁偏角用 `GeomagneticField` 静态查表已够准（±1° 内）。

## 三、方案对比总表

| 维度 | 方案一（推荐） | 方案二 | 方案三 |
|---|---|---|---|
| 满足「随手机旋转」 | ✓ 完整 | ✗ 静止不动 | ✓ 完整+自动校准 |
| 难度 | 中（安卓易/Web 中） | 低 | 高 |
| 新增权限 | 无 | 无 | 无 |
| 新增依赖/库 | 无 | 无 | 无 |
| 电量影响 | 极小（传感器降频 10-15Hz + 页面级启停） | 无 | 同方案一 |
| 真机验收要求 | 需真机（模拟器无磁力计） | 不需要 | 需真机+走动 |
| 风险点 | iOS 权限流程、国产浏览器碎片化 | 不达标 | 调参黑洞 |

## 四、推荐结论

**推荐方案一，且分两步交付**：

- **第一步（安卓端）**：传感器 → bridge → 光锥。用户主战场是安卓真机，此步完成后核心诉求即闭环。改动文件：新增 `HeadingSource.kt`（约 60 行）、`map.html`（drawMe 改造 + setHeading，约 50 行）、`RecordScreen.kt`（传感器接线，约 20 行）。
- **第二步（网页版）**：DeviceOrientation 接入 + 同款光锥。改动文件：`src/gps.ts`（或新增 `heading.ts`，约 80 行，大头是兼容分支）、`map-ui.ts`（约 40 行）。
- 两步各自带测试（安卓单测模拟传感器回调；Web 对平滑函数与 wrap-around 插值写单测——纯数学，好测）。

**视觉设计预案**（贴合现有暖红喜庆风）：琥珀/暖白半透明光锥（锥角约 70°，radial 渐变边缘虚化），叠在现有红点下方，保留呼吸脉冲与精度圈不动。
