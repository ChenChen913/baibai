# 拜拜 App · 地图无法加载问题审核报告

> 审核时间：2026-08-14
> 审核范围：Android 端记录页实时地图（WebView + Leaflet + 高德/OSM 瓦片 + 离线瓦片缓存）
> 用户现象：手机安装后**地图始终无法加载，看不到地图，也看不到实时轨迹**，长期未解决。
> 审核方式：全链路代码审查 + 瓦片服务器可达性实测 + git 历史回溯

---

## 〇、审核结论（Executive Summary）

**地图不是"加载不出来"，而是被自己写的离线缓存逻辑"锁死"了。**

核心根因是一条引入 P0 瓦片预缓存（commit `5474fbc`）时埋下的**锁饥饿**缺陷：

- `TileCache` 的 `get / put / download / preload` 四个方法**全部 `@Synchronized` 同一把锁**；
- 用户点「开始拜年」确定 Home 后，`startPreload()` 会在 `Dispatchers.IO` 上**串行下载约 170 张瓦片**（z13~z16，普通+卫星），整个 `preload()` 持锁不释放（Java 锁可重入，内部 `download()` 不会让出）；
- 与此同时，WebView 每请求一张可见瓦片都会走 `shouldInterceptRequest` → `tileCache.download()`，**全部在锁上排队阻塞**，最长 30~85 秒一张都回不来；
- 这段时间内地图完全空白，画在地图上的实时轨迹自然也看不见——与用户描述**完全吻合**。
- `preloadedFor` 标记是 `remember` 的，App 每次重启归零，所以**每次开始拜年都会重新触发**，表现为"始终无法加载"。

此外还有几个并发与正确性缺陷叠加放大了问题（卫星瓦片 MIME 错配、`shouldInterceptRequest` 同步阻塞 WebView 网络线程、无任何诊断日志等），详见 §3。

**瓦片服务器本身没问题**（§4 实测：高德街道瓦片 200 OK / 14.5KB PNG、卫星瓦片 200 OK / 15.5KB **JPEG**、OSM 200 OK / 6.9KB PNG，两种 UA 均可达）。问题 100% 在客户端代码。

**修复优先级**：P1（锁饥饿，Critical）→ P3（同步阻塞，High）→ P2（卫星 MIME，High）→ P4（诊断，High）→ 其余。修复方案见 §5，全部可在不引入新依赖的前提下完成。

## 三、问题清单（按严重程度分级）

### 🔴 P1 · Critical：预载 preload 独占同步锁，饿死实时瓦片请求

**问题描述**
`TileCache` 的 `get / put / download / preload` 全部标注 `@Synchronized`（同一把对象锁）。`preload()` 内部循环调用 `download()`——由于 Java/Kotlin 内置锁**可重入**，`preload()` 在整个 170 张瓦片下载期间**从不释放锁**。而 WebView 的 `shouldInterceptRequest` 对每一张可见瓦片都要调 `tileCache.download()`，全部在锁上排队，导致记录期间地图长时间空白。

**证据**
- [TileCache.kt#L23](file:///c:/Users/11853/Desktop/AI项目/baibai项目/android/app/src/main/kotlin/io/github/chenchen913/baibai/TileCache.kt#L23) `@Synchronized fun get`
- [TileCache.kt#L30](file:///c:/Users/11853/Desktop/AI项目/baibai项目/android/app/src/main/kotlin/io/github/chenchen913/baibai/TileCache.kt#L30) `@Synchronized fun put`
- [TileCache.kt#L41](file:///c:/Users/11853/Desktop/AI项目/baibai项目/android/app/src/main/kotlin/io/github/chenchen913/baibai/TileCache.kt#L41) `@Synchronized fun download`
- [TileCache.kt#L61](file:///c:/Users/11853/Desktop/AI项目/baibai项目/android/app/src/main/kotlin/io/github/chenchen913/baibai/TileCache.kt#L61) `@Synchronized fun preload`（内部调 `download`，可重入不释放）
- 预载规模：[TileMath.kt#L48-L57](file:///c:/Users/11853/Desktop/AI项目/baibai项目/android/app/src/main/kotlin/io/github/chenchen913/baibai/TileMath.kt#L48-L57) z13~z16 × ±0.02° × 普通+卫星 ≈ 170 张
- 触发点：[RecordScreen.kt#L493-L501](file:///c:/Users/11853/Desktop/AI项目/baibai项目/android/app/src/main/kotlin/io/github/chenchen913/baibai/RecordScreen.kt#L493-L501)（Home 确定即触发）

**影响估算**（移动网络 200~500ms/张，串行）
- 170 张 × 0.3s ≈ **51 秒**锁被占用；
- 期间所有可见瓦片请求阻塞，地图全白；
- 弱网 1s/张时 ≈ **170 秒**，几乎等于"永远不出图"。

**为什么"始终"复现**
`preloadedFor` 用 `remember { mutableStateOf<String?>(null) }`，App 每次冷启动 / 离开记录页再回来都归零，于是每次开始拜年都会重新预载、重新锁死。

**严重程度**：Critical（核心功能完全不可用，直接对应用户主诉）

### 🟠 P3 · High：shouldInterceptRequest 在 WebView 网络线程做同步 HTTP，且全序列化

**问题描述**
`shouldInterceptRequest` 在 WebView 的网络线程上同步调用 `tileCache.download()`（`HttpURLConnection`，connectTimeout=5s / readTimeout=8s）。WebView 的网络线程池有限（通常 4~6 个），叠加 `@Synchronized` 序列化后：
- 正常情况：6 张可见瓦片串行下载 ≈ 1~3 秒（慢但能用）；
- 弱网/单张超时：6 张 × 13s = 78 秒，且 WebView 自身的回退请求线程也被占满，无法自救；
- 即便 `download()` 返回 null 想让 WebView 自取，线程已被占住，回退也快不起来。

## 五、修复方案（具体到文件与改法）

### 修复 P1（Critical）：拆锁，预载与实时请求互不阻塞

**核心思路**：把"读缓存"与"写缓存/下载"拆成不同锁；预载用独立线程池，且**绝不持有读路径的锁**。最小改动方案：

**`TileCache.kt`**：
1. 读路径（`get`）用细粒度锁或 `ConcurrentHashMap`，不再与下载共享 `this` 锁；
2. `download()` 改为：先无锁查缓存命中即返回；未命中时**只锁单个 key 的写入**（按 `cacheKey` 分桶锁，或 `put` 内部对单个文件加锁），不阻塞其他 key 的读/写；
3. `preload()` **不再 `@Synchronized`**，内部 `download()` 各 key 独立加锁，预载与实时请求可并发；
4. 预载并发度限制为 2~3（用 `Semaphore`），避免对高德并发过高被风控。

伪代码：
```kotlin
private val cache = java.util.concurrent.ConcurrentHashMap<String, ByteArray>()
private val keyLocks = java.util.concurrent.ConcurrentHashMap<String, Any>()
private val preloadSemaphore = java.util.concurrent.Semaphore(3)

fun get(url: String): ByteArray? = fileFor(url).takeIf { it.exists() }?.let { runCatching { it.readBytes() }.getOrNull() }

fun download(url: String, isPreload: Boolean = false): ByteArray? {
    get(url)?.let { return it }
    if (isPreload) preloadSemaphore.acquire()
    try {
        val lock = keyLocks.computeIfAbsent(TileMath.cacheKey(url)) { Any() }
        synchronized(lock) {           // 只锁单个 key
            get(url)?.let { return it } // double-check
            val bytes = httpGet(url) ?: return null
            put(url, bytes)
            return bytes
        }
    } finally { if (isPreload) preloadSemaphore.release() }
}

fun preload(urls: List<String>): Int { /* 不再 @Synchronized，循环调 download(u, isPreload=true) */ }
```

**`RecordScreen.kt`**：`shouldInterceptRequest` 调 `download(u)`（默认 `isPreload=false`），与预载互不阻塞。

**验收**：开始拜年后立即出图（<3s），预载在后台继续，两者不互相卡死。

### 修复 P3（High）：shouldInterceptRequest 不做同步阻塞 HTTP

**核心思路**：拦截层只做"缓存命中即返回"，未命中时**返回 null 让 WebView 自取**（WebView 的 Chromium 网络栈自带并发与重试，比我们手撸 `HttpURLConnection` 快得多）；下载入库改为**异步回填**（WebView 取到瓦片后我们无法截获字节，所以改为：未命中时启动一个异步任务下载该 URL 入库，下次命中即用）。

**`RecordScreen.kt#shouldInterceptRequest`** 改为：
```kotlin
override fun shouldInterceptRequest(view, request): WebResourceResponse? {
    val u = request?.url?.toString() ?: return null
    if (!isTile(u)) return null
    val bytes = tileCache.get(u)          // 只查缓存，命中才返回
    if (bytes == null) {
        scope.launch(Dispatchers.IO) { tileCache.download(u) } // 异步回填，不阻塞
        return null                        // 让 WebView 自取（快、并发、自带重试）
    }
    val mime = if (u.contains("style=6")) "image/jpeg" else "image/png"  // 顺带修 P2
    return WebResourceResponse(mime, null, 200, "OK", headers, ByteArrayInputStream(bytes))
}
```

**收益**：首屏瓦片由 WebView 并发拉取（4~6 并发 vs 原来 1 并发），出图速度提升数倍；弱网下 WebView 自带超时/重试，不再假死；离线（已预载）时仍走缓存秒出。

## 九、后续追加（2026-08-20）：真机仍有"地图不显示/定位不准"的残留根因与修复

> 背景：P1~P7 落地后真机安装仍偶发两类主诉。二次排查锁定两个残留根因并已修复。

### R1 · 地图不显示残留根因：P3 修复被回退，拦截层又回到同步阻塞

- P3 曾改为"命中才注入、未命中放行 WebView 自取"，后因"部分国产 ROM 从 file:// 自取 https 瓦片不稳"回退为同步注入字节；
- 同步 `download()` 单张最长阻塞 4s+5s，弱网（乡村常见）下 WebView 网络线程池（4~6 个）全部占满 → 地图空白可达分钟级；且 OSM 回退需攒 6 次 tileerror，拦截阻塞下 error 事件极慢，自救迟。
- **修复**：`TileCache.downloadFast(url, 1200ms)`——命中秒回；未命中最多等 1.2s，超时放行 WebView 自取，后台专用 2 线程池继续下载回填（与预载池隔离）；map.html 加看门狗：页面加载 10s 内街道层零成功 → 立即回退 OSM，不再干等 6 次 tileerror。

### R2 · 定位不准根因：双源坐标系混用（安卓特有，网页版无此问题）

- 国产 ROM 的网络定位（WiFi/基站）由高德/百度服务提供，返回 **GCJ-02**；GPS 返回 **WGS-84**。`SystemLocationSource` 原来两源无差别混入同一缓冲；
- 首定 Home 时 GPS 冷启动未锁定，前 3 个 fix 多为网络点 → Home 被定在 GCJ-02 坐标系，随后 GPS 点（WGS-84）与 Home 相距 300~600m；地图层对全部点做 WGS→GCJ 转换，网络点被二次转换 → 标记偏离道路约 500m；
- **修复**：① 双源网关——GPS 点到达后 8s 内丢弃网络点；基站粗定位（acc>300m）一律丢弃；无 GPS 时网络点照旧放行（快速首定/室内兜底）；② 首定 Home 改攒 3 个高精度 fix（≤50m）或 10s 超时，不再拿任意 3 个点凑数；③ 新增 `LocationSourceTest` 5 项网关回归（Robolectric）。
- 代价：GPS 冷启动时「正在获取定位…」可能持续 5~10 秒（原来 3s），换来 Home 坐标系正确；已同步进真机验收清单 §1/§5 与汇总表。
